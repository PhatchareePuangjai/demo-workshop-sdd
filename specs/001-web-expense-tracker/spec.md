## User Scenarios & Testing *(mandatory)*

### User Story 1 - บันทึกรายการและดูภาพรวมการเงิน (Priority: P1)

ผู้ใช้กรอกชื่อรายการ จำนวนเงิน เลือกประเภท (รายรับ / รายจ่าย) และหมวดหมู่ (อาหาร, เดินทาง, ช้อปปิ้ง, อื่น ๆ) แล้วกดบันทึก รายการจะปรากฏในลิสต์ทันที โดยรายการล่าสุดอยู่บนสุด รายรับแสดงเป็นสีเขียว รายจ่ายแสดงเป็นสีแดง และกล่องสรุปด้านบนแสดง รายรับรวม, รายจ่ายรวม และยอดคงเหลือ (รายรับ − รายจ่าย) ที่อัปเดตทันที

**Why this priority**: นี่คือคุณค่าหลักของแอป — ผู้ใช้จดรายการได้และเห็นว่าเงินเข้าออกเท่าไร เหลือเท่าไร แม้ทำเฉพาะเรื่องนี้เรื่องเดียวก็ใช้งานเป็น MVP ได้แล้ว

**Independent Test**: เปิดแอปที่ยังไม่มีข้อมูล → เพิ่มรายรับ 1 รายการและรายจ่าย 1 รายการ → ตรวจว่าลิสต์แสดงถูกต้อง สีถูกต้อง และกล่องสรุปทั้ง 3 ค่าตรงกับผลรวมที่คำนวณด้วยมือ

**Acceptance Scenarios**:

1. **Given** ผู้ใช้กรอกชื่อ "เงินเดือน" จำนวน 25000 ประเภทรายรับ, **When** กดบันทึก, **Then** รายการ "เงินเดือน" ปรากฏบนสุดของลิสต์เป็นสีเขียวและแสดงจำนวนเงิน "25,000.00 บาท"
2. **Given** มีรายการอยู่แล้ว, **When** ผู้ใช้เพิ่มรายจ่าย "ข้าวมันไก่" 60 หมวด "อาหาร", **Then** รายการใหม่อยู่เหนือรายการเดิมทั้งหมด เป็นสีแดง และแสดงหมวดหมู่ "อาหาร" กำกับ
3. **Given** รายรับรวม 25,000.00 และรายจ่ายรวม 1,250.00, **When** ผู้ใช้ดูกล่องสรุป, **Then** แสดงรายรับรวม "25,000.00 บาท", รายจ่ายรวม "1,250.00 บาท" และยอดคงเหลือ "23,750.00 บาท"
4. **Given** รายจ่ายรวมมากกว่ารายรับรวม, **When** ผู้ใช้ดูกล่องสรุป, **Then** ยอดคงเหลือติดลบและแสดงเป็นสีแดง
5. **Given** ผู้ใช้ปล่อยชื่อรายการว่าง (หรือมีแต่ช่องว่าง), **When** กดบันทึก, **Then** ระบบไม่บันทึก แสดงข้อความแจ้งข้อผิดพลาดที่มองเห็นได้ และรายการในลิสต์ไม่เปลี่ยนแปลง
6. **Given** ผู้ใช้กรอกจำนวนเงินที่ว่าง, เป็น 0, ติดลบ หรือไม่ใช่ตัวเลข, **When** กดบันทึก, **Then** ระบบไม่บันทึก แสดงข้อความแจ้งข้อผิดพลาดที่มองเห็นได้ และรายการในลิสต์ไม่เปลี่ยนแปลง
7. **Given** ยังไม่มีรายการใดเลย, **When** ผู้ใช้เปิดแอป, **Then** แสดงข้อความต้อนรับ "ยังไม่มีรายการ เริ่มบันทึกรายรับ-รายจ่ายแรกของคุณได้เลย!" และกล่องสรุปทั้ง 3 ค่าแสดง "0.00 บาท"

### User Story 2 - ข้อมูลไม่หายเมื่อปิดหรือรีเฟรช (Priority: P2)

รายการทั้งหมดที่ผู้ใช้บันทึกไว้ต้องยังอยู่ครบเมื่อรีเฟรชหน้าหรือปิดแล้วเปิดเบราว์เซอร์ใหม่ พร้อมกล่องสรุปที่ตรงกับรายการเหล่านั้น

**Why this priority**: ถ้าข้อมูลหายทุกครั้งที่ปิดหน้า แอปจะใช้เป็นสมุดบัญชีจริงไม่ได้ แต่ต้องมีการบันทึกรายการ (Story 1) ก่อนจึงจะทดสอบเรื่องนี้ได้

**Independent Test**: เพิ่มหลายรายการ → รีเฟรชหน้า → ปิดแล้วเปิดเบราว์เซอร์ใหม่ → ตรวจว่ารายการ ลำดับ สี หมวดหมู่ และยอดสรุปเหมือนเดิมทุกประการ

**Acceptance Scenarios**:

1. **Given** มีรายการที่บันทึกไว้หลายรายการ, **When** ผู้ใช้รีเฟรชหน้า, **Then** รายการทั้งหมดปรากฏครบตามลำดับเดิมและกล่องสรุปแสดงค่าเดิม
2. **Given** มีรายการที่บันทึกไว้, **When** ผู้ใช้ปิดเบราว์เซอร์แล้วเปิดแอปใหม่, **Then** รายการทั้งหมดยังอยู่ครบ
3. **Given** ผู้ใช้แก้ไขหรือลบรายการแล้ว, **When** รีเฟรชหน้า, **Then** ผลของการแก้ไข/ลบยังคงอยู่ (ไม่ย้อนกลับเป็นค่าเก่า)

---

### User Story 3 - กรองดูเฉพาะรายรับหรือรายจ่าย (Priority: P2)

ผู้ใช้เลือกมุมมองของลิสต์ได้ 3 แบบ: "ทั้งหมด", "เฉพาะรายรับ", "เฉพาะรายจ่าย" เพื่อโฟกัสดูเงินเข้าหรือเงินออกอย่างเดียว

**Why this priority**: ช่วยให้ผู้ใช้วิเคราะห์ว่าเงินเข้า/ออกไปกับเรื่องใดเมื่อรายการเริ่มเยอะ แต่แอปยังใช้งานได้ถ้าไม่มีตัวกรอง

**Independent Test**: เพิ่มรายรับและรายจ่ายอย่างละหลายรายการ → สลับตัวกรองทั้ง 3 แบบ → ตรวจว่าลิสต์แสดงเฉพาะประเภทที่เลือก และกล่องสรุปไม่เปลี่ยน

**Acceptance Scenarios**:

1. **Given** มีทั้งรายรับและรายจ่าย, **When** ผู้ใช้เลือก "เฉพาะรายรับ", **Then** ลิสต์แสดงเฉพาะรายรับ (เรียงล่าสุดไว้บน)
2. **Given** มีทั้งรายรับและรายจ่าย, **When** ผู้ใช้เลือก "เฉพาะรายจ่าย", **Then** ลิสต์แสดงเฉพาะรายจ่าย (เรียงล่าสุดไว้บน)
3. **Given** ผู้ใช้เลือกตัวกรองใดอยู่, **When** เลือก "ทั้งหมด", **Then** ลิสต์แสดงทุกรายการ
4. **Given** ผู้ใช้เลือกตัวกรองใดก็ตาม, **When** ดูกล่องสรุป, **Then** ค่ารายรับรวม รายจ่ายรวม และยอดคงเหลือยังคำนวณจากรายการทั้งหมด ไม่เปลี่ยนตามตัวกรอง
5. **Given** มีรายการแต่ไม่มีรายการที่ตรงกับตัวกรองที่เลือก (เช่น มีแต่รายรับแต่เลือก "เฉพาะรายจ่าย"), **When** ดูลิสต์, **Then** แสดงข้อความสั้น ๆ ว่าไม่มีรายการในมุมมองนี้ (ไม่ใช่ข้อความต้อนรับของกรณียังไม่มีรายการเลย)

### User Story 4 - แก้ไขรายการที่บันทึกไว้ (Priority: P3)

ผู้ใช้แก้ไขชื่อรายการและจำนวนเงินของรายการที่บันทึกไว้แล้วได้ เมื่อแก้เสร็จ กล่องสรุปทั้ง 3 ค่าคำนวณใหม่ทันที

**Why this priority**: ช่วยแก้กรณีกรอกผิด ทำให้ไม่ต้องลบแล้วเพิ่มใหม่ แต่ไม่จำเป็นต่อการใช้งานพื้นฐาน

**Independent Test**: เพิ่มรายการ 1 รายการ → แก้ไขชื่อและจำนวนเงิน → ตรวจว่าลิสต์แสดงค่าใหม่และกล่องสรุปสะท้อนจำนวนเงินใหม่

**Acceptance Scenarios**:

1. **Given** มีรายจ่าย "กาแฟ" 60, **When** ผู้ใช้แก้ชื่อเป็น "กาแฟเย็น" และจำนวนเป็น 75 แล้วยืนยัน, **Then** ลิสต์แสดง "กาแฟเย็น" "75.00 บาท" และรายจ่ายรวมกับยอดคงเหลือคำนวณใหม่ทันที
2. **Given** ผู้ใช้อยู่ระหว่างแก้ไขรายการ, **When** ล้างชื่อจนว่าง หรือกรอกจำนวนเงินเป็น 0 / ติดลบ / ไม่ใช่ตัวเลข แล้วยืนยัน, **Then** ระบบไม่บันทึกการแก้ไข แจ้งข้อผิดพลาดที่มองเห็นได้ และรายการยังคงเป็นค่าเดิม
3. **Given** ผู้ใช้อยู่ระหว่างแก้ไขรายการ, **When** ยกเลิกการแก้ไข, **Then** รายการกลับเป็นค่าเดิมโดยไม่มีการเปลี่ยนแปลง
4. **Given** ผู้ใช้แก้ไขรายการที่ไม่ได้อยู่บนสุดของลิสต์, **When** บันทึกการแก้ไข, **Then** ตำแหน่งของรายการในลิสต์ไม่เปลี่ยน และประเภท/หมวดหมู่ของรายการยังคงเดิม

---

### User Story 5 - ลบรายการและล้างข้อมูลทั้งหมด (Priority: P3)

ผู้ใช้ลบรายการทีละรายการได้ โดยระบบถามยืนยันก่อนลบ และมีปุ่ม "ล้างข้อมูลทั้งหมด" เพื่อลบทุกรายการพร้อมกัน

**Why this priority**: จำเป็นสำหรับการดูแลรักษาข้อมูล แต่เป็นงานเสริมเมื่อเทียบกับการบันทึกและดูรายการ

**Independent Test**: เพิ่มหลายรายการ → ลบ 1 รายการโดยกดยืนยัน → ลองลบอีกรายการแล้วกดยกเลิก → กด "ล้างข้อมูลทั้งหมด" → ตรวจผลในลิสต์และกล่องสรุปทุกขั้นตอน

**Acceptance Scenarios**:

1. **Given** มีหลายรายการ, **When** ผู้ใช้กดลบรายการหนึ่งและยืนยัน, **Then** รายการนั้นหายจากลิสต์ รายการอื่นไม่เปลี่ยน และกล่องสรุปคำนวณใหม่ทันที
2. **Given** ผู้ใช้กดลบรายการหนึ่ง, **When** ระบบถามยืนยันแล้วผู้ใช้ปฏิเสธ/ยกเลิก, **Then** รายการยังอยู่ครบและยอดสรุปไม่เปลี่ยน
3. **Given** มีหลายรายการ, **When** ผู้ใช้กด "ล้างข้อมูลทั้งหมด" และยืนยัน, **Then** ทุกรายการถูกลบ ลิสต์แสดงข้อความต้อนรับสำหรับกรณีไม่มีรายการ และกล่องสรุปทั้ง 3 ค่าเป็น "0.00 บาท"
4. **Given** ผู้ใช้กด "ล้างข้อมูลทั้งหมด", **When** ระบบถามยืนยันแล้วผู้ใช้ปฏิเสธ/ยกเลิก, **Then** ไม่มีรายการใดถูกลบ

---

### Edge Cases

- **ชื่อรายการยาวมาก** (เช่น 200 ตัวอักษร หรือข้อความยาวที่ไม่มีเว้นวรรค): ข้อความต้องขึ้นบรรทัดใหม่และอยู่ในกรอบของการ์ดรายการ ไม่ล้นขอบจอ และไม่ทำให้หน้าเลื่อนแนวนอน
- **ชื่อที่มีแต่ช่องว่าง**: ถือว่าเป็นชื่อว่าง ต้องถูกปฏิเสธ
- **จำนวนเงินไม่ถูกต้อง**: ว่าง, 0, ติดลบ, ตัวอักษร, หรือตัวเลขที่ไม่สมบูรณ์ ต้องถูกปฏิเสธ และข้อมูลที่ผู้ใช้กรอกไว้ในฟอร์มยังอยู่เพื่อให้แก้ไขได้ โดยไม่ต้องกรอกใหม่ทั้งหมด
- **จำนวนเงินมีทศนิยมเกิน 2 ตำแหน่ง** (เช่น 12.345): ปัดเป็นทศนิยม 2 ตำแหน่งตั้งแต่ตอนบันทึก (เป็น 12.35) เพื่อให้จำนวนที่แสดงในลิสต์กับยอดในกล่องสรุปตรงกันเสมอ หากปัดแล้วได้ 0.00 (เช่น 0.001) ถือว่าไม่ใช่จำนวนที่มากกว่า 0 และต้องถูกปฏิเสธ
- **จำนวนเงินมาก** (หลักล้านขึ้นไป): แสดงคั่นหลักพันครบถ้วนและอ่านได้ในกล่องสรุปและลิสต์โดยไม่ล้นกรอบ
- **ยอดคงเหลือเท่ากับ 0**: ไม่ถือว่าติดลบ จึงไม่แสดงเป็นสีแดงเตือน
- **เพิ่มรายการใหม่ขณะเลือกตัวกรองอยู่**: รายการถูกบันทึกและกล่องสรุปอัปเดตทันที ส่วนลิสต์ยังเป็นไปตามตัวกรองที่เลือกอยู่ (รายการที่ไม่ตรงตัวกรองจะไม่แสดงจนกว่าผู้ใช้จะเปลี่ยนมุมมอง)
- **ลบรายการสุดท้ายที่เหลืออยู่**: ระบบกลับไปแสดงข้อความต้อนรับสำหรับกรณีไม่มีรายการ
- **กด "ล้างข้อมูลทั้งหมด" ตอนไม่มีรายการ**: ไม่เกิดข้อผิดพลาดและไม่มีสิ่งใดเปลี่ยนแปลง
- **ข้อมูลที่เก็บไว้ในเครื่องเสียหาย/อ่านไม่ได้**: แอปต้องเปิดได้ตามปกติในสถานะไม่มีรายการ ไม่แสดงหน้าว่างหรือค้าง
- **รีเฟรชหน้าระหว่างที่กำลังแก้ไขรายการ**: การแก้ไขที่ยังไม่ยืนยันถูกทิ้ง รายการกลับเป็นค่าที่บันทึกไว้ล่าสุด
- **หน้าจอขนาดเล็ก** (สมาร์ตโฟน): ฟอร์ม ตัวกรอง กล่องสรุป และปุ่มต่าง ๆ ต้องใช้งานได้ครบโดยไม่ต้องเลื่อนแนวนอน

## Requirements *(mandatory)*

### Functional Requirements

**การเพิ่มรายการ (Create)**

- **FR-001**: ผู้ใช้ต้องสามารถเพิ่มรายการใหม่โดยระบุ ชื่อรายการ, จำนวนเงิน และประเภท (รายรับ / รายจ่าย) แล้วกดบันทึกเพื่อเพิ่มเข้าลิสต์ได้
- **FR-002**: ผู้ใช้ต้องสามารถเลือกหมวดหมู่ของรายการจากตัวเลือก "อาหาร", "เดินทาง", "ช้อปปิ้ง", "อื่น ๆ" ได้ และหากไม่ได้เลือกให้ใช้ "อื่น ๆ" เป็นค่าเริ่มต้น
- **FR-003**: ระบบต้องปฏิเสธการบันทึกเมื่อชื่อรายการว่าง (รวมถึงมีแต่ช่องว่าง) และแสดงข้อความแจ้งข้อผิดพลาดที่ผู้ใช้มองเห็นได้
- **FR-004**: ระบบต้องปฏิเสธการบันทึกเมื่อจำนวนเงินไม่ใช่ตัวเลขที่มากกว่า 0 และแสดงข้อความแจ้งข้อผิดพลาดที่ผู้ใช้มองเห็นได้
- **FR-005**: เมื่อบันทึกสำเร็จ ระบบต้องล้างฟอร์มให้พร้อมกรอกรายการถัดไป และซ่อนข้อความข้อผิดพลาดเดิม (ถ้ามี) แต่เมื่อบันทึกไม่สำเร็จเพราะข้อมูลไม่ถูกต้อง ข้อมูลที่ผู้ใช้กรอกไว้ต้องยังอยู่ในฟอร์มเพื่อให้แก้ไขต่อได้

**การดูและกรองรายการ (Read & Filter)**

- **FR-006**: ระบบต้องแสดงรายการทั้งหมดโดยเรียงจากรายการที่เพิ่มล่าสุดไว้ด้านบน
- **FR-007**: ระบบต้องแสดงรายรับเป็นสีเขียวและรายจ่ายเป็นสีแดง โดยแต่ละรายการแสดง ชื่อ, จำนวนเงิน, ประเภท และหมวดหมู่ ให้แยกแยะได้ชัดเจน
- **FR-008**: ระบบต้องมีตัวกรอง 3 แบบ ได้แก่ "ทั้งหมด", "เฉพาะรายรับ", "เฉพาะรายจ่าย" โดยค่าเริ่มต้นคือ "ทั้งหมด" และตัวกรองที่เลือกอยู่ต้องมองเห็นได้ชัดเจน
- **FR-009**: ตัวกรองมีผลกับรายการที่แสดงในลิสต์เท่านั้น ไม่มีผลต่อค่าในกล่องสรุป
- **FR-010**: ระบบต้องแสดงกล่องสรุปด้านบน 3 ค่า ได้แก่ รายรับรวม, รายจ่ายรวม และยอดคงเหลือ (= รายรับรวม − รายจ่ายรวม) คำนวณจากรายการทั้งหมดและอัปเดตทันทีหลังการเพิ่ม แก้ไข หรือลบทุกครั้งโดยไม่ต้องรีเฟรชหน้า

**การแก้ไขรายการ (Update)**

- **FR-011**: ผู้ใช้ต้องสามารถแก้ไขชื่อรายการและจำนวนเงินของรายการที่บันทึกไว้แล้วได้ และสามารถยกเลิกการแก้ไขโดยไม่เปลี่ยนแปลงรายการได้
- **FR-012**: การแก้ไขต้องใช้กฎตรวจสอบเดียวกับการเพิ่มรายการ (FR-003, FR-004) หากไม่ผ่านต้องไม่บันทึกและรายการต้องคงค่าเดิม
- **FR-013**: การแก้ไขรายการต้องไม่เปลี่ยนตำแหน่ง ประเภท หรือหมวดหมู่ของรายการนั้น

**การลบรายการ (Delete)**

- **FR-014**: ผู้ใช้ต้องสามารถลบรายการทีละรายการได้ โดยระบบต้องถามยืนยันก่อนลบทุกครั้ง และไม่ลบหากผู้ใช้ปฏิเสธ
- **FR-015**: ระบบต้องมีปุ่ม "ล้างข้อมูลทั้งหมด" ที่ลบทุกรายการพร้อมกัน โดยถามยืนยันก่อนลบและไม่ลบหากผู้ใช้ปฏิเสธ

**การคงอยู่ของข้อมูล (Persistence)**

- **FR-016**: ระบบต้องเก็บรายการทั้งหมดไว้ในเครื่องของผู้ใช้ เพื่อให้ข้อมูลไม่สูญหายเมื่อรีเฟรชหน้าหรือปิดแล้วเปิดเบราว์เซอร์ใหม่ และการเพิ่ม แก้ไข ลบ ทุกครั้งต้องถูกบันทึกทันที
- **FR-017**: หากไม่สามารถอ่านข้อมูลที่เก็บไว้ได้ ระบบต้องเริ่มทำงานในสถานะไม่มีรายการแทนที่จะขัดข้อง

**ประสบการณ์ใช้งาน (User Experience)**

- **FR-018**: จำนวนเงินทุกจุดที่แสดง (ลิสต์และกล่องสรุป) ต้องคั่นหลักพันด้วยจุลภาค มีทศนิยม 2 ตำแหน่ง และตามด้วยหน่วย "บาท" เช่น "1,250.00 บาท"
- **FR-019**: เมื่อยอดคงเหลือติดลบ (น้อยกว่า 0) ต้องแสดงยอดคงเหลือเป็นสีแดง
- **FR-020**: ชื่อรายการที่ยาวต้องขึ้นบรรทัดใหม่ภายในกรอบของรายการ ไม่ล้นหลุดขอบจอ
- **FR-021**: เมื่อยังไม่มีรายการใดเลย ต้องแสดงข้อความต้อนรับ "ยังไม่มีรายการ เริ่มบันทึกรายรับ-รายจ่ายแรกของคุณได้เลย!" และเมื่อมีรายการแล้วต้องซ่อนข้อความนี้
- **FR-022**: เมื่อมีรายการแต่ไม่มีรายการที่ตรงกับตัวกรองที่เลือก ต้องแสดงข้อความสั้น ๆ ว่าไม่มีรายการในมุมมองนั้น แทนข้อความต้อนรับ
- **FR-023**: หน้าตาของแอปต้องปรับการแสดงผลให้อ่านและใช้งานได้ครบทุกฟังก์ชันทั้งบนคอมพิวเตอร์และสมาร์ตโฟน

**รูปลักษณ์ (Visual Identity)**

- **FR-024**: หน้าตาของแอปต้องใช้ธีมสีและสไตล์ตามภาพอ้างอิงที่ทีมกำหนด (โทนอบอุ่น สดใส เป็นมิตรแบบการ์ตูนน่ารัก): พื้นหลังโทนครีม-พีชอ่อน, สีหลัก (ปุ่มบันทึก และตัวกรองที่เลือกอยู่) เป็นสีส้ม, การ์ด ปุ่ม ช่องกรอก และป้ายมีมุมโค้งมนและขอบสีครีม, ชื่อแอปเป็นตัวหนาสีส้มมีขอบขาว และกล่องสรุปทั้ง 3 กล่องมีสีพื้นพาสเทลต่างกัน (เขียวมิ้นต์ / ชมพูอมส้ม / เหลือง สำหรับรายรับรวม / รายจ่ายรวม / ยอดคงเหลือ)
- **FR-025**: ข้อความทุกส่วนต้องอ่านง่ายบนพื้นหลังที่อยู่ติดกัน (อัตราส่วนความต่างสีไม่ต่ำกว่า 4.5:1 สำหรับข้อความปกติ และไม่ต่ำกว่า 3:1 สำหรับข้อความขนาดใหญ่) และรายรับ/รายจ่าย/ยอดติดลบต้องยังแยกด้วยสีเขียว/แดงตาม FR-007 และ FR-019 (ปรับเฉดสีได้เพื่อให้ผ่านเกณฑ์นี้)
- **FR-026**: ห้ามนำตัวการ์ตูน โลโก้ หรือไอคอนของบุคคลอื่นจากภาพอ้างอิงมาใช้ และห้ามพึ่งภาพหรือฟอนต์จากภายนอก (ใช้ได้เฉพาะสี รูปทรง และอีโมจิมาตรฐาน) เพื่อให้แอปแสดงผลครบถ้วนแม้ไม่ได้ออนไลน์

### Key Entities *(include if feature involves data)*

- **รายการ (Entry)**: หนึ่งรายการรายรับหรือรายจ่าย ประกอบด้วย ชื่อรายการ (ข้อความ), จำนวนเงิน (ตัวเลขมากกว่า 0), ประเภท (รายรับ หรือ รายจ่าย), หมวดหมู่ (อาหาร / เดินทาง / ช้อปปิ้ง / อื่น ๆ) และเวลาที่เพิ่ม (ใช้เรียงลำดับล่าสุดไว้บน) ชื่อและจำนวนเงินแก้ไขได้ ส่วนประเภทและหมวดหมู่กำหนดตอนเพิ่มรายการ
- **สรุปยอด (Summary)**: ค่าที่คำนวณจากรายการทั้งหมด ได้แก่ รายรับรวม, รายจ่ายรวม และยอดคงเหลือ ไม่ถูกเก็บแยกต่างหาก
- **มุมมองตัวกรอง (Filter View)**: ตัวเลือกปัจจุบันของลิสต์ (ทั้งหมด / เฉพาะรายรับ / เฉพาะรายจ่าย) มีผลต่อการแสดงผลของลิสต์เท่านั้น

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: ผู้ใช้เพิ่มรายการใหม่ 1 รายการได้ภายใน 15 วินาที นับจากเริ่มกรอกจนเห็นรายการปรากฏในลิสต์
- **SC-002**: หลังการเพิ่ม แก้ไข หรือลบทุกครั้ง กล่องสรุปทั้ง 3 ค่าตรงกับผลรวมที่คำนวณด้วยมือจากรายการทั้งหมด 100% และเห็นผลทันทีโดยไม่ต้องรีเฟรชหน้า
- **SC-003**: หลังรีเฟรชหน้าหรือปิด-เปิดเบราว์เซอร์ใหม่ รายการที่บันทึกไว้ยังอยู่ครบ 100% (ทดสอบกับอย่างน้อย 50 รายการ) โดยชื่อ จำนวนเงิน ประเภท หมวดหมู่ และลำดับตรงกับก่อนปิด
- **SC-004**: ความพยายามบันทึก/แก้ไขด้วยข้อมูลไม่ถูกต้อง (ชื่อว่าง หรือจำนวนเงินว่าง, 0, ติดลบ, ไม่ใช่ตัวเลข) ถูกปฏิเสธ 100% พร้อมข้อความแจ้งที่มองเห็นได้ และไม่มีข้อมูลผิดเข้าไปอยู่ในลิสต์หรือยอดสรุป
- **SC-005**: จำนวนเงินทุกค่าที่แสดงอยู่ในรูปแบบคั่นหลักพัน ทศนิยม 2 ตำแหน่ง และหน่วย "บาท" 100% และยอดคงเหลือติดลบแสดงเป็นสีแดงทุกครั้ง
- **SC-006**: หน้าจอใช้งานได้ครบทุกฟังก์ชันโดยไม่ต้องเลื่อนแนวนอน ตั้งแต่ความกว้างขนาดสมาร์ตโฟน (ประมาณ 360 พิกเซล) จนถึงหน้าจอคอมพิวเตอร์
- **SC-007**: ชื่อรายการที่ยาว 200 ตัวอักษร (ทั้งแบบมีเว้นวรรคและไม่มีเว้นวรรค) แสดงอยู่ในกรอบของรายการทั้งหมดในทุกขนาดหน้าจอที่รองรับ
- **SC-008**: ผู้ใช้ที่ไม่เคยใช้แอปมาก่อนทำขั้นตอน เพิ่มรายการ → กรอง → แก้ไข → ลบ ได้สำเร็จโดยไม่ต้องมีคำแนะนำ ภายใน 3 นาที
- **SC-009**: ข้อความทุกส่วนในหน้าจอมีอัตราส่วนความต่างสีตามเกณฑ์ใน FR-025 ครบ 100% (ตรวจจากคู่สีตัวอักษร/พื้นหลังทุกคู่ที่ใช้จริง)
- **SC-010**: ผู้ตรวจที่วางภาพหน้าจอแอปเทียบกับภาพอ้างอิงระบุได้ว่าโทนสี (ครีม-พีช, ส้ม, เขียวมิ้นต์, ชมพู, เหลือง) และรูปทรงมุมโค้งมาจากชุดเดียวกัน โดยไม่มีตัวการ์ตูนหรือโลโก้จากภาพอ้างอิงปรากฏในแอป

## Assumptions

- **ผู้ใช้และอุปกรณ์**: ใช้งานคนเดียวบนเบราว์เซอร์เครื่องเดียว ไม่มีระบบล็อกอิน/บัญชีผู้ใช้ และไม่มีการซิงก์ข้อมูลข้ามเครื่องหรือข้ามเบราว์เซอร์ (ข้อมูลอยู่เฉพาะในเบราว์เซอร์ของเครื่องที่ใช้)
- **ขอบเขตงาน**: เป็นเว็บหน้าเดียว ไม่มี Backend และต้องพัฒนาให้เสร็จภายใน 1 ชั่วโมง 15 นาที ตามโจทย์ (`specs/โจทย์/team-1.md`) และหลักการในรัฐธรรมนูญโครงการ ส่วนรายละเอียดด้านเทคนิคจะกำหนดในขั้นตอนวางแผน (`/speckit-plan`)
- **นอกขอบเขต**: การค้นหา, การกรองตามหมวดหมู่, การกรองตามวันที่, กราฟ/รายงาน, การส่งออกข้อมูล, การเลิกทำ (undo), หลายสกุลเงิน, การแก้ไขประเภทหรือหมวดหมู่ของรายการเดิม (หากต้องการเปลี่ยนให้ลบแล้วเพิ่มใหม่)
- **สกุลเงินและภาษา**: ใช้สกุลเงินบาทอย่างเดียว และส่วนติดต่อผู้ใช้เป็นภาษาไทย
- **หมวดหมู่**: มี 4 หมวดคงที่ ใช้ร่วมกันทั้งรายรับและรายจ่าย และหากผู้ใช้ไม่เลือกให้ถือเป็น "อื่น ๆ"
- **การเรียงลำดับ**: เรียงตามเวลาที่เพิ่มรายการ (ล่าสุดไว้บน) และการแก้ไขไม่เปลี่ยนลำดับ
- **กล่องสรุป**: คำนวณจากรายการทั้งหมดเสมอ ไม่ขึ้นกับตัวกรองที่เลือก (โจทย์ไม่ได้ระบุ จึงเลือกตีความแบบนี้เพราะยอดคงเหลือควรสะท้อนภาพรวมการเงินจริง)
- **การยืนยันก่อนล้างทั้งหมด**: โจทย์ระบุให้ถามยืนยันเฉพาะการลบทีละรายการ แต่ถือว่าปุ่ม "ล้างข้อมูลทั้งหมด" ซึ่งกระทบทุกรายการควรถามยืนยันด้วยเพื่อป้องกันการกดพลาด
- **การปัดทศนิยม**: จำนวนเงินที่มีทศนิยมเกิน 2 ตำแหน่งยอมรับได้ โดยปัดเป็น 2 ตำแหน่งตั้งแต่ตอนบันทึก ทั้งค่าที่แสดงและค่าที่ใช้คำนวณยอดสรุปจึงเป็นค่าเดียวกัน และจำนวนที่ปัดแล้วต้องมากกว่า 0
- **ประเภทเริ่มต้นในฟอร์ม**: โจทย์ไม่ได้ระบุค่าเริ่มต้นของประเภท จึงกำหนดให้ฟอร์มเริ่มที่ "รายจ่าย" (ประเภทที่ผู้ใช้บันทึกบ่อยที่สุด) และผู้ใช้เปลี่ยนได้ก่อนกดบันทึก
- **ยอดคงเหลือเป็นบวกหรือศูนย์**: ไม่มีข้อกำหนดสีพิเศษ (แสดงด้วยสีปกติ) เพราะโจทย์กำหนดสีเฉพาะกรณีติดลบ
- **ภาพอ้างอิงด้านรูปลักษณ์**: ใช้เป็นแรงบันดาลใจด้านโทนสีและสไตล์เท่านั้น ค่าสีที่ใช้จริงกำหนดในขั้นวางแผน สีข้อความบางส่วนจึงเข้มกว่าในภาพอ้างอิงเพื่อให้ผ่านเกณฑ์ความอ่านง่าย (FR-025) ส่วนการตกแต่งเพิ่มเติมจำกัดที่รูปทรง สี และอีโมจิมาตรฐาน (FR-026) และการปรับหน้าตานี้ไม่เปลี่ยนหน้าที่การทำงานใด ๆ ของแอป
